# 블로그 글 수집 개선: 설계 스펙

- 작성일: 2026-09-24
- 상태: 설계 승인 대기
- 관련 파일: `src/fetch_article.py`, `src/collect.py`, `my_sources.txt`

## 1. 문제

`my_sources.txt` 에 블로그 URL 을 넣으면 매일 브리핑에 합류하는 기능은 이미 있다.
그러나 RSS 를 스스로 선언하지 않는 블로그에서 조용히 무너진다.

실측(2026-09-24, `discover_and_fetch` 현재 구현):

| 대상 | 결과 | 소요 |
|---|---|---|
| `blog.naver.com/adcsk` | 목록 5건 ✅ | 0.8s |
| `jojoldu.tistory.com/` | 목록 5건 ✅ | 3.9s |
| `brunch.co.kr/@svillustrated` | 목록 5건 ✅ | 1.1s |
| `velog.io/@teo` | **쓰레기 1건** (`teo (teo.v) / 작성글 - velog`, 27자) | 0.9s |
| `medium.com/daangn` | **0건** | 6.6s |
| `d2.naver.com/home` | **쓰레기 1건** (44자) | 0.8s |
| `www.oopy.io` | **쓰레기 1건** (62자) | **17.0s** |

### 1.1 가장 큰 문제는 0건이 아니라 '쓰레기 1건'

`discover_and_fetch` 5단계 폴백은 HTML 이 받아지기만 하면 무조건 1건을 만든다.
목록·프로필 페이지가 '글 하나'로 둔갑해 브리핑 카드로 올라온다.
조용한 실패(0건)보다 나쁘다. 리포트 품질을 직접 떨어뜨리면서도 품질 게이트를 통과한다.

### 1.2 실패한 곳들은 전부 피드가 있었다

주소 규칙을 몰랐을 뿐이다. 실측으로 확인:

```
velog.io/@teo      → v2.velog.io/rss/@teo      20건
medium.com/daangn  → medium.com/feed/daangn    10건
medium.com/@user   → medium.com/feed/@user     10건
d2.naver.com/home  → d2.naver.com/d2.atom      20건
```

`fetch_article.py` 에는 이미 네이버 블로그용 특례(1.5절)가 하드코딩돼 있다.
**그 패턴을 표로 일반화하는 것**이 해법이다.

### 1.3 실패가 비싸다

한 소스 실패에 최대 17초. 재시도 3회 × 지수 백오프(2·4·8초) + `feedparser` 자체 타임아웃 없음.
소스가 늘수록 수집 시간이 선형으로 늘고, GitHub Actions 실행 시간을 잠식한다.

## 2. 범위

### 하는 것
- RSS 를 선언하지 않는 블로그 플랫폼 대응 (규칙표)
- 목록·프로필 페이지가 글로 둔갑하는 것 차단
- 실패 비용(시간) 상한
- 어느 경로로 수집됐는지 관측 가능하게

### 하지 않는 것 (YAGNI)
- 본문 전체 수집: RSS 요약 180자 유지
- 키워드 검색 수집 (네이버/구글 검색 API): 검토했으나 제외
- 온디맨드 단발 CLI: 매일 파이프라인 합류만
- 과거글 아카이빙 / 페이지네이션
- 헤드리스 브라우저(JS 렌더 사이트): 실측 실패 4건이 전부 브라우저 없이 해결되므로 과잉

## 3. 접근안 비교

| 안 | 내용 | 판정 |
|---|---|---|
| **A. 플랫폼 규칙표** | 네이버 특례를 표로 일반화 + 폴백 가드 + 타임아웃 | **채택.** 의존성 0, 실측 실패 4건 전부 해결, 확장은 한 줄 |
| B. 범용 HTML 목록 파서 | 피드 없으면 글 링크를 휴리스틱으로 추출 | 기각. 정확도 낮고 사이트 개편마다 깨진다. 육안 검수가 필요해지면 무인 운영 취지에 어긋남 |
| C. 헤드리스 브라우저 | Playwright 로 JS 렌더까지 | 기각. Actions 실행시간·용량 부담이 큰데 실측 실패는 전부 브라우저 없이 해결됨 |

## 4. 설계

### 4.1 해석 체인

`discover_and_fetch` 를 순서가 명시된 5단계로 재정리한다.

```
① URL 자체가 피드인가
② 플랫폼 규칙표에 걸리는가        ← 신규 (네이버 특례를 흡수)
③ HTML 이 선언한 피드가 있는가     (link rel=alternate)
④ origin 에 흔한 피드 경로가 있는가 ← 경로 있는 URL 에도 시도하도록 수정
⑤ 단일 글인가                    ← 가드 통과할 때만 (신규)
```

현재와 달라지는 점:

- ② 신규. 네이버 특례(현 1.5절)는 이 표로 흡수돼 하드코딩이 사라진다.
- ③ 을 ④ 보다 **앞으로** 옮긴다. 어차피 ⑤ 를 위해 HTML 을 받아야 하고,
  사이트가 스스로 선언한 피드가 추측 경로보다 정확하다.
- ④ 의 `if parts.path in ("", "/")` 조건을 제거한다.
  `d2.naver.com/home`, `velog.io/@teo` 가 이 조건 때문에 통째로 건너뛰어졌다.
- ⑤ 에 가드를 건다 (4.3).

각 단계는 성공 시 **어느 단계였는지**를 함께 돌려준다 (4.5).

### 4.2 플랫폼 규칙표

```python
PLATFORM_FEEDS = [
    (r"blog\.naver\.com/(?:.*blogId=)?([\w-]+)", "https://rss.blog.naver.com/{0}.xml"),
    (r"velog\.io/@([\w.-]+)",                    "https://v2.velog.io/rss/@{0}"),
    (r"medium\.com/(@?[\w.-]+)",                 "https://medium.com/feed/{0}"),
    (r"d2\.naver\.com",                          "https://d2.naver.com/d2.atom"),
]
```

- 미디엄 패턴은 `@` 를 **보존**한다. `medium.com/@user` → `feed/@user`,
  `medium.com/daangn` → `feed/daangn`. 둘 다 실측 10건 확인.
- 브런치는 **넣지 않는다.** `brunch.co.kr/rss/@필명` 은 0건이고(실측),
  내부 ID 형태(`@@ZKB`)라야 하는데 URL 에서 알 수 없다.
  이미 ③ HTML 자동탐지로 5건 성공하므로 규칙이 불필요하다.
- 티스토리·워드프레스도 넣지 않는다. ③/④ 로 이미 해결된다.

규칙표는 **검증된 것만** 넣는다. 새 플랫폼은 실측 후 한 줄 추가한다.

### 4.3 단일글 폴백 가드

`accept_as_article(url, page) -> bool` 로 분리한다. 아래를 **모두** 만족해야 글로 인정한다.

1. `og:type` 이 `article` **이거나** 기존 `fetch_text()` 추출 본문이 200자 이상
2. URL 의 마지막 경로 세그먼트가 루트(빈 경로 또는 `/`)도,
   `@` 로 시작하는 프로필 세그먼트(`/@teo`)도 아님

실측 대입:

| 대상 | 본문 | 판정 |
|---|---|---|
| `velog.io/@teo` | 27자, 프로필 | 차단 |
| `d2.naver.com/home` | 44자 | 차단 |
| `www.oopy.io` | 62자, 루트 | 차단 |
| `jojoldu.tistory.com/885` | 2130자 | 통과 |

임계값 200자의 근거: 실측 쓰레기 3건이 27~62자, 정상 글이 2130자로 한 자릿수 이상 벌어진다.
경계에 놓인 사례가 없으므로 정밀 튜닝은 불필요하다.

### 4.4 시간 예산

- `_fetch_html`: 재시도 3→2회, 타임아웃 15→8초
- `feedparser` 호출을 타임아웃 컨텍스트로 감싼다. `feedparser.parse()` 에는
  타임아웃 인자가 없어 `socket.setdefaulttimeout` 을 쓴다.

```python
@contextlib.contextmanager
def _socket_timeout(sec: float):
    old = socket.getdefaulttimeout()
    socket.setdefaulttimeout(sec)
    try:
        yield
    finally:
        socket.setdefaulttimeout(old)
```

전역 상태를 건드리므로 **반드시 복원**한다. 실측 검증: 도달 불가 호스트에서
기본값 21.2초 → `timeout=3` 3.4초, 복원 후 `None` 으로 되돌아옴 확인.

효과: 소스당 최악 17초 → 약 5초.

### 4.5 관측성: 기존 V3 품질 철학 유지

각 소스가 **어느 경로로** 수집됐는지 남긴다.

```
[내소스] velog.io/@teo    수집 5건 (플랫폼규칙)
[내소스] jojoldu.tistory  수집 5건 (자동탐지)
[내소스] www.oopy.io      수집 0건 (피드없음·목록페이지)
```

`collect.py` 는 이를 집계해 `data/quality_*.json` 에 추가한다.

```json
"내소스_해석경로": {"플랫폼규칙": 2, "자동탐지": 1, "실패": 1}
```

이유: "왜 이 블로그가 안 들어왔지" 를 Actions 로그 없이 품질기록만으로 진단할 수 있다.
Actions 로그는 수십 일 뒤 삭제되지만 `quality_*.json` 은 커밋돼 남는다.
`diagnose-brief-send` 스킬 및 README 의 V3 철학과 같은 방향이다.

품질 게이트(exit 1) 조건은 **바꾸지 않는다.** 내소스는 원래 선택 기능이고,
0건이 곧 장애는 아니다.

### 4.6 모듈 경계

이 설계의 핵심은 네트워크를 타는 부분과 판단하는 부분을 갈라놓는 것이다.

| 함수 | 네트워크 | 책임 |
|---|---|---|
| `resolve_feed(url) -> str \| None` | **없음** | 규칙표 조회. 순수 함수 |
| `accept_as_article(url, page) -> bool` | **없음** | 폴백 가드 판정. 순수 함수 |
| `discover_and_fetch(url) -> list[dict]` | 있음 | 체인 실행 |

판단 로직이 순수 함수라야 네트워크 없이 테스트된다. 4.7 이 여기에 의존한다.

## 5. 테스트

이 레포는 pytest 가 아니라 **단독 실행 스크립트** 관례를 쓴다
(`python tests/test_promo.py`, 실패를 모아 마지막에 한 번 출력). CI 에는 테스트 단계가 없다.
`tests/test_fetch_blog.py` 도 같은 형식을 따른다.

기본 실행은 **네트워크를 타지 않는다**:

- `resolve_feed()`: URL → 기대 피드 URL (4.2 의 4개 플랫폼 + 규칙에 없는 URL 은 `None`)
- `accept_as_article()`: 27/44/62자 및 프로필·루트 URL 거절, 2130자 글 통과
- 회귀: 네이버 블로그가 기존과 동일한 피드 URL 로 해석되는지

네트워크 통합 테스트는 `--network` 플래그로만 돈다 (기본 스킵).
1절 실측 7개 대상을 그대로 확인한다.

## 8. 열린 위험

- **플랫폼 피드 주소 변경**: 벨로그 `v2.velog.io` 는 비공식 경로다. 끊기면 해당 소스가
  ③④ 로 흘러 0건이 된다. 4.5 의 해석경로 기록으로 조기 발견할 수 있다.
- **`socket.setdefaulttimeout` 전역성**: 같은 프로세스의 다른 네트워크 호출에도 영향을 준다.
  컨텍스트 매니저로 범위를 좁히고 반드시 복원한다.
- **200자 임계값**: 짧은 글(단문 블로그)이 차단될 수 있다. 현재 소스에는 해당 사례가 없고,
  차단 시 사유가 로그에 남으므로 발견 가능하다.
