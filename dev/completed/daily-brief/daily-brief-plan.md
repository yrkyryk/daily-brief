# Daily Brief 자동화 리포트 프로젝트 계획

> 업무 자동화 포트폴리오 아이템 선정 워크북(출발점 A) 결과를 실행 계획으로 옮긴 문서.
> 데이터 분석가 지원용 포트폴리오 프로젝트.

## 0. 한 문장 정의 (워크북 관문 ①)

> **트렌드 수집기가 매일 아침 8시 30분에 자동으로 돌아서, 홍보가 제외된 핵심 뉴스와 실무 인사이트 블로그 글만 골라 Notion에 Daily Brief로 준다.**

- 무엇: 뉴스·블로그 트렌드 수집기
- 언제: 매일 08:30 (KST), 내가 실행하지 않아도
- 누구에게: 나 자신 (원래 매일 눈으로 확인하던 루틴 대체)
- 무엇을: 필터링·분류된 Daily Brief (Notion DB + 인터랙티브 리포트)

## 1. 직무 연결 (워크북 관문 ②)

웹 크롤링/RSS 수집 → 노이즈 제거·정제 → 조건별 필터링/분류 → Notion DB 자동 적재 및 대시보드 업데이트.
이는 데이터 분석가 공고의 **'웹/외부 데이터 파이프라인 구축, 데이터 전처리, 지표 모니터링 대시보드 관리'** 와 동일한 구조다.

> 이 프로젝트가 증명하는 역량: 데이터 파이프라인 설계 / 멱등 적재 / 결정론적 품질 검증 / 스케줄 운영 / 실패 복구.

### 2.1 필터링 규칙 (사람/기계 경계 구체화)

**기계(스크립트, 무료·결정론적):**
- 홍보/광고 제거: 제목·본문에 광고 문구 키워드("협찬", "광고", "제휴", "AD", "sponsored" 등), UTM 파라미터 링크, 보도자료 패턴 필터
- 중복 제거: URL 정규화 + 제목 정규화 해시로 유니크
- 카테고리 분류: 소스 태그 + 키워드 규칙(경제/사회/연예/실무)

**AI 보조(규칙으로 애매한 것만 Claude API 호출):**
- 규칙 필터를 통과했지만 홍보성 의심이 남는 항목의 '읽을 가치' 최종 판정
- 카테고리별 3~5줄 요약 생성

**사람(내가 판단):**
- 그날 Brief 중 실제로 무엇을 열어 읽을지
- 필터가 놓친 것/과하게 거른 것을 주간 회고로 규칙에 반영

## 3. 벤치마킹 (워크북 PART 2)

| 케이스 | 빌릴 것 | 바꿀 것 |
|--------|---------|---------|
| **A13** GitHub Actions + 시크릿 트렌드 리포트 | cron 스케줄 구조, API 키를 코드 밖에서 관리 | AI 트렌드 RSS → 개인 뉴스·블로그, 최신순 → 홍보 제거 + 관심도 필터, 결과는 Notion DB |

| **A11** 슬래시 커맨드 + 크론 업무 에이전트 | 반복 절차를 커스텀 커맨드로 표준화 후 크론 연결 | 주1회 → 매일 08:30, `/daily-brief` 수동 재실행 지원, 산출물을 Slack → Notion |

> 벤치마킹 금지선 통과: 데이터·주기·산출물을 모두 내 것으로 바꿈.

## 4. 기술 스택

- **언어**: Python 3.11+
- **수집**: `feedparser`(RSS), `httpx` + `selectolax`/`beautifulsoup4`(RSS 없는 소스 정적 파싱)
- **적재/저장**: DuckDB (로컬 파일 DB, `(url_hash, collected_date)` 유니크로 멱등성 보장)
- **판정 보조**: Claude API (`claude-haiku-4-5`, 애매 항목·요약만 호출하여 비용 최소화)
- **산출물**:
  - Notion: 공식 Notion API로 Daily Brief DB에 적재
  - 인터랙티브 리포트: 정적 HTML(탭·카테고리·검색) → GitHub Pages 배포
- **스케줄/실행**: GitHub Actions cron (`schedule: cron: '30 23 * * *'`)
- **시크릿**: GitHub Actions Secrets (Notion 토큰, Claude API 키). A13 교훈대로 `.env`는 로컬 개발 전용, 커밋 금지
- **품질 게이트**: 자체 `/daily-brief` 커맨드 + 품질 체크 스크립트(종료 코드로 성공/실패 신호)

## 5. 실행 순서 (워크북 PART 4, 순서 변경 금지)

각 단계는 앞 단계의 완료 기준을 만족한 뒤에만 다음으로 넘어간다. **스케줄 연결을 먼저 하면 무엇이 실패했는지 모른다.**

| 단계 | 완료 기준 | 남길 증거 |
|------|-----------|-----------|
| 1. 손으로 한 번 | 자동화 없이 소스 3~5개에서 손으로 기사를 모아 Brief 1건을 끝까지 만들어 본다. 진짜 절차·필터 규칙이 드러난다 | 손으로 만든 Brief 1건, 소스 목록, 초안 필터 규칙 |
| 2. 수집 스크립트 | 명령 한 번으로 원본 기사가 파일(JSONL)로 떨어진다 | 수집 로그, 원본 저장 파일 |
| 3. 적재 (멱등성) | 같은 데이터를 두 번 넣어도 중복 없이 결과가 안 깨진다 | 2회 실행 후 행 수 동일 로그 |
| 4. 자동 점검 | 데이터가 깨지면(빈 응답·건수 급감·중복 급증) 스스로 알아채고 멈춘다 | 품질 체크리스트 출력표, 일부러 깨본 실패 기록 |
| 5. 산출물 생성 | 사람이 읽을 Daily Brief(Notion + HTML 리포트)로 나온다 | Notion 페이지 스크린샷, 리포트 URL |
| 6. 스케줄 + 실패 알림 | 내가 실행 안 해도 매일 08:30 돌고, 실패하면 알려준다 | 연속 실행 로그, 실패 → 복구 기록 |

## 6. 사용 스킬 (워크북 7번 보완)

**찾아 쓸 것 (3개):**
- `python-patterns` / `python-testing` : 파이프라인 코드 구조·테스트
- `dataviz` : 인터랙티브 리포트 차트 규범
- `deployment-patterns` : GitHub Actions 스케줄·시크릿 운영

**직접 만들 것 (1개, 포트폴리오 하이라이트):**
- **`/daily-brief` 커스텀 커맨드 + `brief-qa` 품질 스킬**
  - 입력 형식: 수집된 JSONL
  - 실행: 규칙 필터 → 애매 항목 AI 판정 → 품질 6개 항목 점검 → 실패 시 종료 코드 1
  - 결과 예시: 카테고리별 정제된 Brief + 품질 리포트
  - 이 '직접 만든 스킬 1개'가 면접에서 제일 눈에 띄는 지점

## 7. 품질 체크리스트 (V3, 매 실행 출력)

1. 소스별 수집 건수 (0건이면 소스 차단 의심 → 실패)
2. 전체 대비 홍보 필터 제거율 (비정상적으로 높/낮으면 규칙 점검)
3. 중복률 (급증 시 정규화 로직 점검)
4. 빈 응답 감지 (직전 실행 대비 건수 급감 임계 초과 → 중단)
5. 카테고리 미분류 비율
6. AI 판정 호출 건수/비용 (예산 상한 초과 시 경고)

실패 시: 적재 롤백 + 실패 사유를 담은 GitHub Issue 자동 생성. 다음 실행 때 빠진 구간만 재수집.

## 8. 리스크 및 대응

| 리스크 | 대응 |
|--------|------|
| 소스에 RSS가 없음 | 정적 HTML 파싱으로 폴백, 그래도 안 되면 소스 교체 |
| 소스 구조 변경/차단 | 품질 체크 4번(빈 응답 감지)이 잡아냄. A13도 43일 후 수집 차단으로 멈춤 → 실패 기록 자체가 제출물 |
| Notion API 토큰 준비 | 착수 전 Notion 인테그레이션 생성 + DB 공유 필요 (사전 준비물) |
| Claude API 비용 | 규칙 우선으로 호출 최소화, 예산 상한 + 호출 건수 로깅 |
| 인스타그램 미포함 | MVP 범위에서 명시적으로 제외, v2 확장 아이디어로 문서화 |

## 10. 산출물 정의 (완료 기준)

- 2주 이상 무인 운영된 GitHub Actions 실행 로그

- 인터랙티브 리포트 URL
